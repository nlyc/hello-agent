### 2.3 指标

- 工具调用：AST 匹配（函数名精确 + 参数无序 + 值语义等价），按类别准确率。
- QA：准精确匹配（数字/字符串/列表归一化）、包含匹配、引用覆盖率。
- 质量：程序化约束（天数/预算/必含/避开）+ LLM Judge 四维（1–5）+ Win Rate（交换 A/B）。
- 效率：上下文 tokens、packets、LLM 调用、端到端耗时。

### 3.6 在线 S0 vs S1（`deepseek-flash`，项目 `.env` Key）

命令：

```powershell
py -3.14 scripts/eval_online_v2.py --suites tool_calling --limit 12 --out .cache/eval_online_full
py -3.14 scripts/eval_online_v2.py --suites qa --limit 9 --out .cache/eval_online_full
py -3.14 scripts/eval_online_v2.py --suites quality --limit 3 --out .cache/eval_online_full
```

**工具调用（S0 ReAct，12 例）**

| 类别 | 样本 | 通过 | 准确率 |
|---|---:|---:|---:|
| simple | 4 | 2 | 0.500 |
| multiple | 3 | 1 | 0.333 |
| parallel | 2 | 2 | 1.000 |
| irrelevance | 3 | 3 | 1.000 |
| **合计** | **12** | **8** | **0.667** |

平均单例耗时 8.19 s。失败主因是**过度调用**：simple/multiple 中模型额外调用了 `search_notes`；另外 `search_notes.query` 是自由文本，AST 严格匹配把「故宫闭馆」与「故宫 周一 闭馆」判为不等。

**Function Calling 对照（12 例）**：`FunctionCallAgent` 同样 **8/12**，类别完全一致（simple 2/4、multiple 1/3、parallel 2/2、irrelevance 3/3），平均 10.94 s。说明瓶颈不在“文本协议 vs 原生 FC”，而在模型选择与数据集判定口径。

**调优后（工具描述收紧 + 最少调用约束 + free-text 宽松匹配）**

| 范式 | 调优前 | 调优后 | 说明 |
|---|---:|---:|---|
| ReAct | 8/12 | **12/12（1.000）** | simple 4/4、multiple 3/3、parallel 2/2、irrelevance 3/3 |
| Function Calling | 8/12 | **11/12（0.917）** | 唯一失败：simple_03 一次并行调用 3 次 `search_notes`，属于过度调用 |

关键干预不是换协议，而是：
1. 工具描述明确边界（`search_notes` 只用于具体事实；`get_attraction` 只用于景点推荐）；
2. 提示词要求“只调用完成任务所需的最少工具”；
3. `query` 等自由文本参数启用 token 重叠匹配（「故宫闭馆」≡「故宫 周一 闭馆 开放时间」）。

**旅行 QA（S0 原始 RAG vs S1 ContextRAG，9 例）**

| 系统 | 通过 | 包含匹配率 | QEM | 引用覆盖 | 平均耗时 | 平均回答 tokens |
|---|---:|---:|---:|---:|---:|---:|
| S0 RAG | 9/9 | 1.000 | 0.000 | 1.000 | 8.48 s | 48.3 |
| S1 ContextRAG | 8/9 | 0.889 | 0.000 | 1.000 | 8.80 s | 72.8 |

S1 唯一失败为 `qa_02`：回答用「平缓路线可以避开爬坡」改写，未包含标准答案「适合不爬坡的游客」；语义正确但包含匹配未命中。S1 平均回答更长、耗时略高。  
QEM 为 0 是因为两套系统都输出完整解释而非单词答案；此数据集更适合看包含匹配与引用覆盖。

**行程质量（S0 直答 vs S1 ContextRAG，3 例 + 同模型 Judge）**

| 系统 | 约束通过 | 通过率 | Judge 平均 | 平均耗时 | 平均 tokens |
|---|---:|---:|---:|---:|---:|
| S0 直答 | 2/3 | 0.667 | 4.42 | 52.86 s | 939 |
| S1 ContextRAG | 3/3 | 1.000 | 3.75 | 37.23 s | 820 |

真实取舍：S1 在**约束遵守**（2/3 → 3/3）与**耗时**（52.9 → 37.2 s）上更好；但同模型 Judge 给分更低（4.42 → 3.75），因为 S1 严格引用资料，会明确说“颐和园票价资料未提供”，而 S0 更敢写细节。  
例：S0 的 `it_01` 方案很完整（Judge 4.25），但写「不安排故宫」，违反 `must_include=故宫`；S1 保留故宫并避开周一，约束全过。

## 5. 错误分析

| 现象 | 原因 | 处理 |
|---|---|---|
| 负基线工具调用 0 分 | `NoToolAgent` 从不调用工具 | 预期；用于验证指标 |
| 在线工具 simple/multiple 失分 | 模型额外调用 `search_notes`；自由文本 query 严格匹配 | 收紧描述 + 最少调用 + 宽松 query 后，ReAct 12/12、FC 11/12 |
| FC simple_03 仍失败 | 一次响应并行调用 3 次 `search_notes` | 过度调用；原生 FC 需要更明确的“单工具优先”策略 |
| 在线 QA QEM 0 | 回答是完整解释，不是单词答案 | 以包含匹配为主；QEM 保留给短答案基准 |
| S1 QA `qa_02` 未命中 | 改写为「避开爬坡」，未包含标准短语 | 语义正确；包含匹配局限 |
| S0 质量 `it_01` 漏故宫 | 「不安排故宫」被正向包含判定修正后判失败 | 约束判定已修；这是真实违规 |
| S1 质量 Judge 更低 | 严格引用资料，明确说票价未提供 | 真实取舍：合规 vs 丰富度 |
| 上下文 Demo 首次运行 token 为负 | 小语料下六分区标题固定开销 | 改为 20 轮历史对照后 +48% |

## 6. 结论与选型建议

1. **ContextBuilder 不是“全面提升”，而是明确取舍**：质量约束 2/3 → 3/3、耗时 52.9 → 37.2 s；但同模型 Judge 4.42 → 3.75，QA 9/9 → 8/9。它让回答更受资料约束，代价是丰富度与改写自由度。
2. **NoteTool 在单轮 QA 上不提分**（6 例 5/6 → 5/6，tokens +18%），但跨会话 blocker 与“资料不足”表达更稳；价值在长期任务而非单题。
3. **TerminalTool 适合探索式任务**：攻略、日志、代码库不必全部预索引；离线 Demo 已验证 JIT 链路。
4. **MCP 是功能等价层**：6 例 3/6 → 5/6 属小样本波动，不能归因协议；价值在复用与跨客户端。
5. **A2A + 真实规划师可用**：3 例约束全过、通过 2/3、Judge 3.75；但端到端 63.2 s，明显慢于单 Agent。
6. **工具调用已从 8/12 提升到 ReAct 12/12、FC 11/12**：关键不是换协议，而是工具描述明确边界、提示词要求最少调用、自由文本参数宽松匹配；FC 仍有一次并行过度调用。
7. **评估必须先客观后主观**：AST/QEM/程序化约束先行，LLM Judge 只做补充；同模型 Judge 存在自我偏好。

## 7. 威胁与局限

- **在线对比范围有限**：S0/S1 有较完整样本；S2/S4 仅 6 例，S5 仅 3 例，不能做统计结论。
- **样本规模小**：12 + 9 + 6，质量在线仅 3 例，不足以做统计显著性结论。
- **同模型 Judge**：S5 与 S0/S1 都用 `deepseek-flash` 评审，存在自我偏好；S5 的 63 s 也包含 Judge 时间。
- **LLM Judge 偏差**：长度偏好、位置偏好、自我偏好；S0/S1 用同一模型评审，结论需谨慎。
- **单一模型/单一领域**：`deepseek-flash`，结论主要适用于旅行助手与中文语料。
- **ReAct 文本协议**：parallel 按“调用集合覆盖”计分；工具调用中的自由文本参数仍按严格 AST 比对。
- **离线 Embedder**：Hashing 模式语义弱于 FastEmbed；S0 数字来自 M8 的同一口径。
